# XDR/CAP-Coverage Audit Tool and Indexer-Hardening Guide: Technical Architecture

Technical design for our response to the SCF RFP "XDR/CAP-Coverage Audit Tool and Indexer-Hardening Guide". This
document can be read on its own, without the grant application. Working evidence for every part described here is
public at [rumblefishdev/xdr-corpus-evidence](https://github.com/rumblefishdev/xdr-corpus-evidence).

## 1. Summary

Every application that reads the Stellar ledger decodes XDR. Shapes that are rare but valid crash these readers or,
worse, are silently dropped, because nobody tests them. We build one shared test kit for them:

| Component | What it does | Who uses it |
| --- | --- | --- |
| **Corpus** | rare but valid ledger and transaction shapes, each emitted by stellar-core, tagged by CAP and protocol, with the values a correct reader must decode | everyone below |
| **Generator** | reproducibly produces the corpus entries that can't be mined from history | corpus maintainers |
| **Replay harness** | delivers the corpus to an indexer through the Galexie data-lake layout and reports *pass / mishandled / dropped* per entry | indexer authors (wallet-backend, stellar-etl, third parties) |
| **Conformance runner** | runs the corpus through the JS, Go and Rust SDKs and reports every divergence from the network or between SDKs | SDK maintainers |
| **Linter** | flags the three ingestion mistakes in Go indexer source | Go indexer authors |
| **Indexer-hardening guide** | which fields core validates, caps, participants-from-meta, muxed and signed-payload handling, checklist; delivered ready to publish on developers.stellar.org | every indexer author, any language |

## 2. Design principles

These come from running two production indexers, the
[Soroban Block Explorer](https://github.com/rumblefishdev/soroban-block-explorer) and the
[Prices API](https://github.com/rumblefishdev/stellar-prices-api). Each answers a failure we actually had.

1. **Expected values come from the network, never from a reader.**
   - **Failure:** our 890 tests passed while we stored the wrong sender for every fee-bump. They compared our parser
     with our own expectations. We verified against Horizon, which for a fee-bump reports the inner transaction's
     source, the same value we stored, so the cross-check showed "30/30 match".
   - **Rule:** expected values are what stellar-core itself recorded: transaction results, ledger-entry changes in the
     meta, event IDs as stellar-rpc `getEvents` returns them, and contract IDs recomputed from the deployer and salt
     the way the protocol computes them.
2. **Corpus bytes are emitted by stellar-core.**
   - Entries are mined from network history or generated by submitting real transactions.
   - Hand-built bytes are allowed only for variants no network has emitted yet, and they are marked `synthetic`.
   - A pattern core would reject is never in the corpus as valid input.
3. **Verdicts come from stored data, never from exit codes or logs.**
   - **Failure:** in our evidence run, wallet-backend's backfill logged the failed batch and **exited 0** after losing
     a whole ledger.
   - **Failure:** in our own pipeline, a single unwritable ledger stalled ingestion for 19 minutes, and the failure was
     reported as success.
   - **Rule:** the harness inspects what the indexer stored.
4. **A clean build proves nothing about a protocol upgrade.**
   - **Failure:** protocol 27 froze both our indexers; the Prices API stalled for six days with no alarm. In protocols
     28 and 30 the new variant sits in a type nested inside the ledger header. Code compiles, then fails on the first
     ledger that carries the variant, hours or days after activation.
   - **Rule:** only decoding such a ledger through the production code path proves support. The corpus holds such
     ledgers, and the harness drives that code path.
5. **The corpus is language-neutral.** It is XDR files plus a JSON manifest. Any pipeline can read it without our
   code.

## 3. Architecture

```
                       ┌──────────────────────────── corpus (XDR + manifest.json) ────────────────────────────┐
 network history ────► │  mined entries                                                                          │
 generator ──────────► │  generated entries (testnet / mainnet passphrase)  per-CAP coverage report            │
 hand-built ─────────► │  synthetic entries (flagged)                       manifest = fresh decode (CI)       │
                       └───────────────┬───────────────────────────────┬───────────────────────────┬────────────┘
                                       │                               │                           │
                         replay harness│                  conformance  │ runner                    │ guide field table
                  ┌────────────────────▼─────────────┐  ┌──────────────▼──────────────┐   ┌────────▼─────────┐
                  │ local S3 in Galexie layout        │  │ js-stellar-sdk  (Node)      │   │ guide + checklist │
                  │   → adapter: start/ingest/observe │  │ go-stellar-sdk  (Go)        │   │ linter rule IDs   │
                  │   → indexer (wallet-backend, …)   │  │ rs-stellar-xdr  (Rust)      │   └──────────────────┘
                  │   → verdict per entry             │  │ → divergence matrix         │
                  └────────────────┬─────────────────┘  └──────────────┬──────────────┘
                                   └────────── findings reports → issues filed upstream ──┘
```

Everything runs offline in Docker, needs no keys or funds, and fits in CI on every pull request.

## 4. Corpus

### 4.1 Entry layout

Already implemented in the evidence repo (`corpus/entries/cap-00NN/<id>/`):

| File | Content |
| --- | --- |
| `FF…--<ledger>.xdr.zst` | the ledger exactly as Galexie wrote it to the data lake, under Galexie's object name (`FF…` = 0xFFFFFFFF − ledger): zstd-compressed `LedgerCloseMetaBatch`. Canonical, by sha256. |
| `ledger-<n>.LedgerCloseMetaBatch.xdr` | the same, decompressed |
| `tx-<first 16 hex of hash>.TransactionEnvelope.xdr` | the target transaction alone, extracted from the ledger file. An SDK release that predates the ledger's protocol can still be tested on the pattern itself. For example, js-stellar-sdk 17.2.x can't decode protocol-30 ledger meta; support arrived in 17.3.0. |
| `generation.json` | generated entries only (mined entries have none): public keys, every submission and stellar-core's answer to it, including the rejected *negative probes* |

### 4.2 Manifest

`manifest.json` is **generated** from the files by a tool, and CI fails if it differs from a fresh decode. The only
hand-written inputs are:
- which transaction and operation an entry is about;
- the CAP and SEP tags;
- the protocol a CAP introduced;
- issue links.

Key fields (draft schema: `corpus/manifest.schema.json`, JSON Schema 2020-12):

| Field | Meaning |
| --- | --- |
| `id`, `cap[]`, `sep[]` | entry identity and tags |
| `protocol.introduced_in` / `protocol.ledger` | where the pattern can first occur / protocol of the captured ledger |
| `network`, `network_passphrase` | testnet, mainnet or local |
| `source.kind` | `mined` / `generated` / `local` / `handcrafted` |
| `synthetic` | the schema enforces `synthetic == (kind == handcrafted)` |
| `files[]` | path, XDR type, encoding, layout, sha256, `derived_from` |
| `core_validates` | whether core validated the field at the heart of the pattern; this links the corpus to the guide's field table |
| `negative_probes[]` | nearby invalid variants and core's rejection, which places the pattern on core's validation boundary |
| `expected` | 12 fields shared by every entry: ledger, tx, operation, results, sources |
| `extra` | the pattern's own decoded values, e.g. signer key, muxed ID, pool ID, asset order |
| `roundtrip`, `check_lcm_golden` | byte-exact decode/encode result and tool version; path to a stellar-core golden LCM where one exists |
| `related[]` | sightings and issues the entry reproduces |

### 4.3 Validation

| Check | Establishes | Runs |
| --- | --- | --- |
| sha256 of every file equals the manifest | the files are the captured ones | CI, every push |
| decode → encode is byte-exact with rs-stellar-xdr | a reference decoder reads and writes the entry losslessly | CI, every push |
| agreement with stellar-core `--check-lcm` goldens, where published | the corpus matches what core itself treats as correct | CI, every push |
| file consistency: the `.zst` decompresses to the `.xdr`; envelope hash = tx hash; every envelope maps to a result | the entry's files agree with each other | CI, every push |
| manifest = fresh decode | no expected value was typed or edited by hand | CI, every push |
| manifest validates against the schema | the schema is enforceable | CI, every push |
| guide field table = manifest `core_validates` | the guide and the corpus can't drift apart | CI, every push |
| regenerating a generated entry keeps the same pattern and core verdicts | the generator reliably produces the pattern | on demand and before each release (needs testnet, 3-8 min per entry) |

Because the Rust decoder also reads the files to build the manifest, the Rust SDK is never checked against itself.
Network-recorded facts are cross-checked independently of any SDK: result codes, ledger-entry changes, RPC event
IDs, and recomputed contract IDs (§2.1).

### 4.4 Coverage plan

**Sizing.** Counting CAPs says little about coverage. There are about 73 live CAPs; many add no shape that a reader
sees, and one CAP can add several. Our coverage tool (prototype: `corpus/tools/coverage-targets.py` in the evidence
repo) counts from the XDR itself. It parses stellar-xdr at every protocol tag from v19 to v30 and lists every union
arm and optional field reachable from `LedgerCloseMetaBatch`. At protocol 30 that is **499 union arms and 28
optional fields**. It dates each arm to the protocol and CAP that added it, and marks which corpus entries contain
it. Its per-CAP view lists every CAP. Some CAPs change behaviour without adding a new XDR shape (e.g. CAP-73's SAC
trustlines); those are covered by known-bug entries (tier A below).

Findings from the three sample entries:
- they already cover 109 arms (22%), mostly through incidental content of their ledgers;
- of the 390 uncovered arms, 237 are result codes; failed operations land in ledgers and can be generated, while
  some transaction-level codes are rejected before a ledger and belong in `negative_probes`;
- 29 of the 38 arms added in protocols 21-30 are uncovered. That is the protocol-upgrade class of failure (§2.4).

Release targets:
- at least 50 entries;
- 100% of the arms added in protocols 21-30 that can occur in a closed ledger;
- at least 90% of all ledger-reachable arms that can occur in a closed ledger;
- every arm classified as *in ledgers*, *rejected by core* or *not in meta*.

The entries fall into three tiers:

| Tier | What | Entries |
| --- | --- | --- |
| A. Known bugs | every RFP-named pattern, every §7 sighting with a distinct shape, and our own production cases (table below) | ~30 |
| B. Protocol 21-30 arms | CAP-77/80 freeze results, upgrade ledgers carrying the new `ConfigSettingEntry` arms, CAP-67 `SCAddress` arms, CAP-71 credentials, CAP-85, empty-transaction-set headers (synthetic until one closes), muxed contract address | ~12 |
| C. Sweep | one entry per operation result code (these entries can share a generated ledger), plus a few mainnet ledgers chosen to cover as many remaining arms as possible | ~8 |

Tier A patterns:

| Pattern | CAP / SEP | Source | Known failure it targets |
| --- | --- | --- | --- |
| signed-payload signer (`P…`, 40–100 bytes) | CAP-40, SEP-23 | mined (done) | wallet-backend #729 halt |
| SAC transfer to a muxed recipient, `to_muxed_id` event | CAP-27, CAP-67 | generated (done) | wallet-backend #716 truncation |
| pool whose issuers sort differently by bytes and by strkey text | CAP-38 | generated (done) | js-stellar-sdk #1766 |
| muxed source on classic operations | CAP-27 | generated | wallet-backend #716 |
| muxed source on Soroban operations | CAP-27 | mined from pre-protocol-25 history, or synthetic | core has rejected it since protocol 25 |
| muxed account and offer IDs that decode to a different ID than they encode | CAP-27 | synthetic (decoder-side) | js-stellar-sdk #1785 |
| maps whose keys collide after native conversion | CAP-46 | generated | js-stellar-sdk #1789 |
| vectors at maximum length, nested ScVal at depth limits | CAP-46 | generated + synthetic | rs-stellar-xdr #581, #598 |
| nested Soroban authorization trees | CAP-46 | generated | wallet-backend ingestion halt (unbounded tree) |
| SAC `trust()` trustline with no trustline state change | CAP-73 | generated | wallet-backend #731 |
| per-operation contract events next to byte-identical diagnostic events | CAP-67 | mined | our own: 83% of Soroban txs lost events; 2.5× inflation from counting diagnostics |
| fee-bump with CAP-67 events | CAP-15, CAP-67 | mined: mainnet tx `358ef42d…75dc`, ledger 62016099 | our own: wrong sender stored; Horizon reports the same value, so verifying against it missed the bug |
| contract deployed by a factory contract | CAP-46 | generated | our own: wrong deployer stored |
| claimable balance ID `B…` (58 chars) and muxed `M…` (69 chars) in address columns | CAP-23, CAP-27 | mined | our own: backfill stopped on a 56-character column |
| SAC event emitted by a non-SAC contract with an asset-like topic | CAP-46 | generated | our own: any contract could add rows to USDC's history |
| CAP-71 V2 address credentials | CAP-71 | generated | auth decoding |
| ledger-header variants from protocols 28 and 30 (e.g. `scpValue.ext` v3) | protocol 28 / 30 | mined | our own: compiles, then fails on the first ledger with the variant |
| empty transaction set under the current protocol | protocol 28+ | synthetic until one closes | decode of empty sets |
| non-UTF-8 bytes and lone surrogates in XDR string arms | — | synthetic (decoder-side) | js-stellar-sdk #1823 |

The coverage report shows every target with its protocol, CAP, class and the entries covering it. CI regenerates it
on every push. Uncovered arms are ranked for new entries by known bugs, then by mainnet rarity, using an
arm-frequency count over the public stellar-etl dataset.

## 5. Generator

Already implemented (`corpus/gen/`, Go, run in a container) for the two generated sample entries. For each pattern
it:
1. creates fresh accounts (friendbot on testnet, root account on a local network);
2. builds the transactions with go-stellar-sdk and submits them through Stellar RPC;
3. submits the nearby invalid variants first and records core's rejection of each.

Galexie then exports the target ledger once the history archive has a checkpoint past it, and the manifest tool
fills in the entry. Generation is reproducible for both testnet and mainnet passphrases:
- **testnet:** entries are generated on testnet itself;
- **mainnet passphrase:** the same generator runs against a private, isolated stellar-core configured with the mainnet
  passphrase. Its only funds are the genesis root account's play-money XLM, and it has no peers. Core signs, hashes
  and emits ledgers exactly as mainnet would, so these entries are core-emitted, not synthetic. Its accounts are fresh
  keys with no mainnet balance, so a leaked transaction cannot execute on the real network.

Patterns that already occurred on mainnet can also be mined from its history.

A regenerated entry has a new tx hash, so regeneration is checked on invariants: the operation, the results, the
pattern's decoded values, and core's verdicts on the probes.

## 6. Replay harness

**Input.** The harness writes corpus ledgers into a local S3 (SeaweedFS) in the Galexie data-lake layout, including
`.config.json`, with one ledger per file. wallet-backend's `datastore` backend reads this layout, and so does
anything built on go-stellar-sdk's `BufferedStorageBackend`. A mock RPC `getLedgers` endpoint is a later adapter
input, not part of the first release.

**Adapter interface.**

```go
type Adapter interface {
    Start(ctx context.Context, src DataLake) error                     // launch the indexer at the local data lake
    Ingest(ctx context.Context, from, to uint32) error                 // run it over a ledger range
    Observe(ctx context.Context, e corpus.Entry) (Observation, error)  // read back what it stored for this entry
    Stop(ctx context.Context) error
}
```

The harness compares each `Observation` with the entry's manifest values and gives a verdict:
- **pass:** everything is stored correctly;
- **mishandled:** something is stored, but values are missing or wrong;
- **dropped:** nothing is stored for the transaction.
Exit codes and logs are recorded but never decide the verdict (§2.3).

**Reference adapter: wallet-backend.** Already prototyped in `sighting-729/`. It:
- builds wallet-backend at any commit in a Go container;
- migrates a fresh TimescaleDB;
- runs `ingest` in backfill mode against the local data lake;
- queries the stored transactions and state changes;
- decodes stored addresses back to strkeys with its own code, independent of wallet-backend.

Two wallet-backend quirks the adapter handles, both found while building the evidence:
- Backfill on an empty database ingests nothing, because it only fills gaps below the latest ingested ledger. The
  adapter seeds one clearly marked placeholder row above the range.
- Backfill exits 0 on a failed batch.

**Memory.** Entries stream one ledger at a time, and the harness has a fixed memory budget that CI enforces with a
corpus larger than the budget. Unbounded memory growth is itself one of the failures under test.

**Acceptance.** The reference adapter reproduces wallet-backend #729, #731 and #716 on pre-fix commits and passes on
the fixed ones. #729 already gives `dropped` before the fix and `pass` after it.

## 7. SDK conformance runner

Each SDK runs in its own pinned container: Node for js-stellar-sdk, Go for go-stellar-sdk, Rust for rs-stellar-xdr
(the XDR library behind the Rust Soroban SDK and the stellar CLI; see §4.3 for why checking it is not circular).
It reads only corpus files and the manifest, nothing typed in by hand. Checks per entry:

1. **XDR layer:** decode, then re-encode to the original bytes.
2. **Transaction layer:** parse the envelope with the SDK's high-level API, and compare the hash and pattern values
   with the manifest.
3. **Domain layer:** the SDK's own helpers, e.g. `Asset.compare`, `LiquidityPoolAsset`, `getLiquidityPoolId`, strkey
   encode/decode of muxed and signed-payload keys, and `scValToNative`.
4. **Ledger-meta layer:** decode the full `LedgerCloseMetaBatch`. Reported separately: meta support often lags
   transaction support.

**Output** is a divergence matrix (entry × SDK × layer). Whenever one SDK diverges, the runner opens sibling issues
in each affected SDK. Fixes have not always crossed SDKs: the Go SDK had already fixed the issuer-ordering bug when
JS still had it.

**Acceptance.** The runner reproduces js-stellar-sdk #1766, #1785 and #1789 on pre-fix tags. #1766 already gives
`mishandled` on 17.2.0 and `pass` on 17.2.1 and on the latest release, 17.4.0; CI runs it on every push.

## 8. Linter (Go)

**What it is.** A static-analysis tool, in the sense of `go vet`, not a code formatter. It reads the source code of a
Go indexer without running it and reports three dangerous patterns in how the code handles ledger data:
- values stellar-core does not validate, used as if they were trusted;
- recursive parsing with no depth or size limit;
- participants taken from the transaction envelope instead of the ledger meta.

The linter and the replay harness catch different things. The harness finds a bug only when the corpus has an input
that triggers it. The linter finds the risky pattern in code before any such input has appeared on the network, and
in indexers the harness has no adapter for. wallet-backend is its acceptance test: the linter must flag every seeded
violation and report nothing on current wallet-backend.

The linter is built on `golang.org/x/tools/go/analysis` and runs as a standalone binary and as a golangci-lint
plugin. We target Go because wallet-backend, stellar-etl and most indexers built on go-stellar-sdk are Go. It has
three rules:

| Rule | Detects | Seeded from |
| --- | --- | --- |
| `XDRL001` unvalidated field trusted | values from fields core does not validate (memo, Soroban auth trees, muxed IDs, event topics) flowing into storage keys, identity or participants without a check. The field list comes from the guide's table. | asset identity read from an event topic without checking that the emitter is the asset's SAC |
| `XDRL002` missing depth or size cap | recursion over `ScVal`, `SorobanAuthorizedInvocation` and similar types without a depth or length bound | wallet-backend's unbounded authorization trees |
| `XDRL003` participants from the envelope | participant or sender derived from `TransactionEnvelope` or operation sources where the meta (`LedgerEntryChanges`, fee-bump outer source) is authoritative | wrong fee-bump sender and wrong factory deployer stored |

Every rule ships with seeded violations taken from the bugs in the table: our own production bugs for rules 1
and 3, wallet-backend's for rule 2. The acceptance check runs it clean on current wallet-backend.

## 9. Indexer-hardening guide

The guide is written for developers.stellar.org. It follows the RFP's fixed outline (items 1–4 and 6) and adds one
section from our own experience (item 5):
1. which transaction fields stellar-core validates (signatures, sequence numbers, fees, time bounds) and which it
   passes through (memos, Soroban auth trees, muxed IDs), as a field-by-field table checked against the manifest;
2. recommended depth and size caps;
3. deriving participants from the meta, with fee-bumps and factory deployments as worked examples;
4. muxed and signed-payload handling, including SEP-23 strkey forms and column sizes (`M…` 69 chars, `B…` 58, `P…`
   up to 165);
5. surviving protocol upgrades: pin tracking, and decoding a new protocol's ledger before the vote. This is the
   watcher we run in production, which opens an issue whenever our pinned `stellar-xdr` lags the protocol core
   already supports;
6. a self-audit checklist mirroring the three linter rules, for indexers in other languages.

Publication requires review by a stellar-core or platform engineer. We request that review as soon as the draft,
with the field table, exists. The guide is delivered ready to publish, as a pull request to the Stellar developer
docs; merging it is the docs maintainers' call.

## 10. CI, release and adoption

- Every tool (generator, harness, conformance runner, linter) has its own test suite.
- Every pull request in the tools' repos runs those tests and the full corpus: round-trip, manifest freshness,
  schema, harness against wallet-backend, and the conformance runner against all three SDKs.
- A **GitHub Action** lets any indexer or SDK run the corpus in its own CI. It is the cheapest way for a third-party
  indexer to adopt the kit.
- **Adoption starts with SDF's own pipeline:** we open a pull request adding the corpus check to wallet-backend's CI.
- Releases are tagged; corpus releases are versioned by the newest protocol covered.

## 11. License, infrastructure and scope

**License.** Apache-2.0 for all code and the corpus.

**Infrastructure and user tracking.** There is no hosted service: everything runs locally or in CI, in Docker (a
local S3, Postgres for the indexer under test, Galexie with captive core, pinned SDK containers). Everything is built
on the current stable Stellar stack (stellar-xdr 30, current js-stellar-sdk and go-stellar-sdk releases) and bumped
with each protocol release. There is no telemetry and no user tracking.

**Scope limits.**
- The linter covers Go only; other languages use the guide's checklist.
- There is one reference adapter (wallet-backend); others can be added through the documented interface.
- The Galexie data-lake input comes first; a mock RPC `getLedgers` input is later work.
- Findings are filed upstream with a reproducing entry, not fixed by us.
- Coverage is measured on arms that can occur in a closed ledger. Arms core rejects before a ledger are recorded as
  negative probes, not corpus entries.

## 12. Disclosure

Ingestion-halting inputs are denial-of-service vectors against production indexers. Halting or crashing findings
are reported privately first, to SDF's security disclosure channel and the affected maintainers. The public issue
and corpus entry follow once a fix is released. Decoding mismatches and non-security defects are filed publicly
right away. Every finding is tracked in the findings report, whichever path it takes.

## 13. Maintenance and protocol upgrades

Our team maintains the kit for 12 months after the production release, with one named maintainer:
- **Each new CAP:** corpus entries for every CAP that ships in that window, including the first protocol upgrade
  after delivery.
- **Each protocol on testnet:** the harness and conformance runner run over the new protocol's ledgers before the
  mainnet vote, with findings filed upstream.
- **Issues:** triaged within 10 business days.
