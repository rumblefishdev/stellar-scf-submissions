# XDR/CAP-Coverage Audit Tool and Indexer-Hardening Guide: Technical Architecture

Technical design for our response to the SCF RFP "XDR/CAP-Coverage Audit Tool and Indexer-Hardening Guide". This
document can be read on its own, without the grant application. Working evidence for every part described here is
public at [rumblefishdev/xdr-corpus-evidence](https://github.com/rumblefishdev/xdr-corpus-evidence).

## 1. Summary

Every application that reads the Stellar ledger decodes XDR. Shapes that are rare but valid crash these readers or,
worse, are silently dropped, because nobody tests them. We build one shared test kit for them:

| Component | What it does | Who uses it |
| --- | --- | --- |
| **Corpus** | rare but valid ledger and transaction shapes, each emitted by stellar-core, tagged by CAP and protocol, with the values a correct reader must decode | everyone below |
| **SDK input vectors** | invalid inputs an SDK may receive from its user (malformed strings, over-limit lengths, out-of-range numbers), each with the error the SDK must give | SDK maintainers |
| **Generator** | reproducibly produces the corpus entries that can't be mined from history, offline, on a private stellar-core | corpus maintainers |
| **Replay harness** | delivers the corpus to an indexer through the Galexie data-lake layout and reports *pass / mishandled / dropped* per entry, or *error* when the run itself failed | indexer authors (wallet-backend, stellar-etl, third parties) |
| **Conformance runner** | runs the corpus and the input vectors through the JS, Go and Rust SDKs and reports every divergence from the network or between SDKs | SDK maintainers |
| **Linter** | flags the three ingestion mistakes in Go indexer source | Go indexer authors |
| **Indexer-hardening guide** | which fields core validates, caps, participants-from-meta, muxed and signed-payload handling, checklist; delivered ready to publish on developers.stellar.org | every indexer author, any language |

## 2. Design principles

These come from running two production indexers, the
[Soroban Block Explorer](https://github.com/rumblefishdev/soroban-block-explorer) and the
[Prices API](https://github.com/rumblefishdev/stellar-prices-api). Each answers a failure we actually had.

1. **Expected values come from the network, never from a reader.**
   - **Failure:** our 890 tests passed while we stored the wrong deployer for every contract created by a factory
     contract. The tests compared our parser with our own expectations, so they shared its mistake.
   - **Rule:** expected values are what stellar-core itself recorded in the ledger: transaction and operation results,
     ledger-entry changes in the meta (including fee processing), and contract IDs as they appear in the meta. Values
     that are conventions rather than ledger data, such as event IDs, are derived from the event's position in the
     meta (ledger, transaction, operation, index) in the format stellar-rpc uses. No expected value depends on
     querying a reader such as Horizon or stellar-rpc.
2. **Corpus bytes are emitted by stellar-core.**
   - Entries are mined from network history, generated by submitting real transactions, or taken from stellar-core's
     own test goldens.
   - Hand-built bytes are allowed only for valid variants no network has emitted yet, and they are marked
     `synthetic`.
   - A pattern core would reject is never in the corpus as valid input. It is recorded as a negative probe.
   - Invalid input that only an SDK's user can produce (malformed strings, over-limit lengths) lives in the separate
     SDK input vectors (§7), never in the corpus.
3. **Verdicts come from stored data, never from exit codes.**
   - **Failure:** in our evidence run, wallet-backend's backfill logged the failed batch and **exited 0** after losing
     a whole ledger.
   - **Failure:** in our own pipeline, a single unwritable ledger stalled ingestion for 19 minutes, and the failure was
     reported as success.
   - **Rule:** the harness inspects what the indexer stored. A control transaction in the same ledger shows whether
     the run itself worked (§6). If the control is stored and the target is not, the target was dropped, whether or
     not the indexer logged anything: that is exactly a silent drop.
4. **A clean build proves nothing about a protocol upgrade.**
   - **Failure:** protocol 27 froze both our indexers; the Prices API stalled for six days with no alarm. In protocols
     28 and 30 the new variant sits in a type nested inside the ledger header. Code compiles, then fails on the first
     ledger that carries the variant, hours or days after activation.
   - **Rule:** only decoding such a ledger through the production code path proves support. The corpus holds such
     ledgers, and the harness drives that code path.
5. **The corpus is language-neutral.** It is XDR files plus a JSON manifest. Any pipeline can read it without our
   code.

## 3. Architecture

```
 network history ──► mined entries ─────────┐
 generator ────────► generated entries ─────┤   corpus: XDR files + manifest.json
 (private core)      (testnet / mainnet     ├─► per-CAP coverage report
                      passphrase)           │   manifest = fresh decode (CI)
 stellar-core ─────► golden entries ────────┤
 hand-built ───────► synthetic entries ─────┘
                                │
       ┌────────────────────────┼─────────────────────────────┐
       ▼                        ▼                             ▼
 replay harness           conformance runner            guide field table
 local S3 (Galexie)       js-stellar-sdk (Node)         + checklist
 → adapter per indexer    go-stellar-sdk (Go)           + linter rule IDs
 → verdict per entry      rs-stellar-xdr, stellar-strkey,
       │                  soroban-sdk (Rust)
       │                  + SDK input vectors
       │                  → divergence matrix
       └──────────┬─────────────┘
                  ▼
        findings report → triage → issues filed upstream
                                   (halting bugs: private disclosure first)
```

Everything runs offline, meaning with no access to any Stellar network: in Docker, with pinned and pre-pulled
images and packages. It needs no keys or funds and fits in CI on every pull request.

## 4. Corpus

### 4.1 Entry layout

Already implemented in the evidence repo (`corpus/entries/cap-00NN/<id>/`):

| File | Content |
| --- | --- |
| `FF…--<ledger>.xdr.zst` | the ledger exactly as Galexie wrote it to the data lake, under Galexie's object name (`FF…` = 0xFFFFFFFF − ledger): zstd-compressed `LedgerCloseMetaBatch`. This captured file is canonical (sha256). It is never re-sorted, because some ledger-entry changes must stay in core's order for downstream consumers. |
| `ledger-<n>.LedgerCloseMetaBatch.xdr` | the same, decompressed |
| `tx-<first 16 hex of hash>.TransactionEnvelope.xdr` | the target transaction alone, extracted from the ledger file. An SDK release that predates the ledger's protocol can still be tested on the pattern itself. For example, js-stellar-sdk 17.2.x can't decode protocol-30 ledger meta; support arrived in 17.3.0. |
| `generation.json` | generated entries only (mined entries have none): public keys, every submission and stellar-core's answer to it, including the rejected *negative probes* |

### 4.2 Manifest

`manifest.json` is **generated** from the files by a tool, and CI fails if it differs from a fresh decode. The only
hand-written inputs are:
- which transactions and operations an entry is about (its target or targets);
- the CAP and SEP tags;
- the protocol a CAP introduced;
- each pattern's invariants (the fields that must not change when the entry is regenerated);
- issue links.

The table below is the **target schema** for the release. The draft schema in the evidence repo
(`corpus/manifest.schema.json`, JSON Schema 2020-12) already has most of it, including `accepted` and per-field
`core_validation[]` records with their evidence. It differs in three places, all planned for Deliverable 1:
- `targets[]`, `pattern_targets[]` and the `decoded`/`network` provenance marks are not there yet;
- `source.kind` and `network` have no `golden` value yet;
- `check_lcm_golden` is a path string, not the record described here.

| Field | Meaning |
| --- | --- |
| `id`, `cap[]`, `sep[]` | entry identity and tags |
| `protocol.introduced_in` / `protocol.ledger` | where the pattern can first occur / protocol of the captured ledger |
| `network`, `network_passphrase` | `pubnet`, `testnet`, `local` or `golden`, with the exact passphrase. Private-network entries carry the passphrase they were generated with. Golden entries carry stellar-core's test passphrase. |
| `source.kind` | `mined` / `generated` / `local` / `golden` / `handcrafted` |
| `synthetic` | the schema enforces `synthetic == (kind == handcrafted)` |
| `files[]` | path, XDR type, encoding, layout, sha256, `derived_from` |
| `targets[]` | the target transactions (one for most entries; one per result code in a sweep entry, §4.4), each with its own expected values |
| `pattern_targets[]` | the coverage targets (union arms, optional fields) this entry claims as its pattern, and so carries expected values for |
| `accepted` | core accepted the target transaction into a ledger |
| `core_validation[]` | one record per transaction field the entry exercises: `{ field, validated, stage, evidence_kind, evidence }`. `stage` is `validation`, `apply` or `host` (Soroban host checks such as auth). `evidence_kind` is `rejected_probe` (proves the field *is* validated), `accepted_probe` (an adversarial value core accepted, which proves it *is not*) or `source_ref` (a CAP or stellar-core source reference). |
| `negative_probes[]` | nearby invalid variants and core's rejection, which places the pattern on core's validation boundary |
| `expected` | fields shared by every target: ledger, tx, operation, results, sources. Each field is marked `decoded` (from rs-stellar-xdr) or `network` (cross-checked by a second decoder, §4.3). |
| `extra` | the pattern's own decoded values, e.g. signer key, muxed ID, pool ID, asset order |
| `roundtrip` | byte-exact decode/encode result and the tool version |
| `check_lcm_golden` | for golden entries and for patterns a golden also covers: the stellar-core commit, test name and section |
| `related[]` | sightings and issues the entry reproduces |

### 4.3 Validation

| Check | Establishes | Runs |
| --- | --- | --- |
| sha256 of every file equals the manifest | the files are the captured ones | CI, every push |
| decode → encode is byte-exact with rs-stellar-xdr | a reference decoder reads and writes the entry losslessly | CI, every push |
| agreement with stellar-core's `--check-lcm` goldens (method below) | the corpus matches what core itself treats as correct | CI, every push |
| file consistency: the `.zst` decompresses to the `.xdr`; envelope hash = tx hash; every envelope maps to a result | the entry's files agree with each other | CI, every push |
| manifest = fresh decode | no expected value was typed or edited by hand | CI, every push |
| `network` fields agree between rs-stellar-xdr and a second decoder (go-stellar-sdk's xdr) | network-recorded expected values don't depend on one decoder | CI, every push |
| manifest validates against the schema | the schema is enforceable | CI, every push |
| every field in the guide's table has at least one `core_validation` record, and all records agree with the table | the guide and the corpus can't drift apart, and a field with no evidence shows up as a gap | CI, every push |
| regenerating every generated entry, offline, under both passphrases, keeps the same pattern and core verdicts | the generator reliably produces the pattern | CI, every push |

**Agreement with stellar-core's goldens.** stellar-core records the LedgerCloseMeta its own unit tests produce
(`test-lcm-current/`, `test-lcm-next/`) and compares new runs against them with `--check-lcm`. Before writing a
golden, core zeroes the non-deterministic diagnostic events but keeps the original order of entries. When comparing,
it sorts copies of both sides. Goldens come from core's own test scenarios, with their own accounts and a test
passphrase, so a ledger we mine or generate is never byte-for-byte comparable with one. We therefore do two things:
1. **Golden entries.** We import stellar-core goldens as corpus entries (`source.kind = golden`, at a pinned
   stellar-core commit). The release contains at least one. The first candidate is
   `test-lcm-current/FrozenLedgerKeysTests/`, for the CAP-77 freeze patterns, which are otherwise hard to produce. CI
   checks that each golden entry still equals its golden at the pinned commit, using core's own comparison
   (diagnostics zeroed, sorted copies).
2. **Structural agreement for other entries.** Where a golden covers the same pattern as a mined or generated entry,
   the two must agree on the pattern's structure, not on values: the same union arms and discriminants, the same
   result codes, and the same kinds of ledger-entry change in the same places. Accounts, amounts and hashes differ by
   design and are not compared.

The same comparison (diagnostics zeroed, sorted copies, never applied to the canonical file) is how we check that a
re-export of a ledger equals its captured file.

**The Rust check is not circular.** The manifest's decoded values come from rs-stellar-xdr, so checking the Rust SDK
against them alone would be circular. Expected fields marked `network` (result codes, ledger-entry changes, event
positions, contract IDs as recorded in the meta) are decoded a second time by go-stellar-sdk's xdr package, and CI
requires the two decoders to agree. Every SDK, Rust included, is then checked against those cross-checked fields.

### 4.4 Coverage plan

**Sizing.** Counting CAPs says little about coverage. One CAP can add several shapes, and many add none that a reader
ever sees. Our coverage tool (prototype: `corpus/tools/coverage-targets.py` in the evidence repo) counts from the
XDR itself. It parses stellar-xdr at every protocol tag from v19 to v30 and lists every union arm and optional field
reachable from `LedgerCloseMetaBatch`. At protocol 30 that is **499 union arms and 28 optional fields** (56 optional
targets, present and absent). It dates each arm to the protocol and CAP that added it, and marks which corpus entries
contain it. CAP tags come from the stellar-xdr history, with a hand-checked override table where commit messages name
the wrong CAP or none. Its per-CAP view lists every CAP. Some CAPs change behaviour without adding a new XDR shape
(e.g. CAP-73's SAC trustlines); those are covered by known-bug entries (tier A below).

Findings from the five sample entries:
- they already contain 123 arms (25%), mostly through incidental content of their ledgers, not their targets;
- of the 376 arms not yet contained, 216 are result codes. Failed operations land in ledgers and can be generated;
  some transaction-level codes are rejected before a ledger and belong in `negative_probes`;
- 27 of the 38 arms added in protocols 21-30 are not yet contained. That is the protocol-upgrade class of failure
  (§2.4).

**Two coverage numbers.** An arm can be in an entry only by accident (some other transaction in the same ledger), so
we report two numbers:
- **pattern coverage:** arms an entry claims in `pattern_targets[]`, with expected values checked by every tool;
- **incidental coverage:** arms that appear anywhere in an entry's files.

**Classification, published in Deliverable 1.** Every arm is classified as *in ledgers*, *rejected by core* or *not
in meta*. Every arm excluded from *in ledgers* carries its evidence (a negative probe or a stellar-core source
reference), so the denominator can be audited.

Release targets:
- at least 50 entries;
- **pattern coverage of 100%** of the arms added in protocols 21-30 that can occur in a closed ledger;
- **incidental coverage of at least 90%** of all arms that can occur in a closed ledger.

## 5. Generator

**Main path: a private, isolated stellar-core.** The generator runs offline, against a private stellar-core network
with no peers outside it and its own local history archive, configured with either the testnet or the mainnet
passphrase. So generation is reproducible for both passphrases, needs no keys or funds, and runs in CI. Core itself
signs, hashes and emits these ledgers, so the entries are core-emitted, not synthetic. Network settings (fees,
limits, validator keys) are the private network's own. The manifest records them, and only patterns whose shape
doesn't depend on them are generated this way.

Topologies:
- **one validator** for almost every pattern;
- **several validators** for patterns that only arise from consensus, such as the CAP-83 empty transaction set.

For each pattern the generator:
1. funds fresh accounts from the private network's genesis root account;
2. builds the transactions with go-stellar-sdk and submits them through Stellar RPC;
3. submits the nearby invalid variants first and records core's rejection of each.

Some patterns need a network configuration change: the new `ConfigSettingEntry` arms, and the CAP-77 frozen keys.
For those, the generator uploads a `ConfigUpgradeSet` and arms the upgrade on the private network's validators, the
same way the public network upgrades its settings.

Galexie then exports the target ledger from the local archive, and the manifest tool fills in the entry. The private
network uses accelerated test settings (short ledger close times and checkpoint interval, as `stellar/quickstart
--local` does), so the archive checkpoint arrives within seconds.

**Safety with the mainnet passphrase.** stellar-core derives the genesis root key from the passphrase, so the private
network's root key is the same as mainnet's root key, which anyone can already derive. On mainnet that account's
master key has weight 0 and it has no other signers, so any transaction signed with it fails with `txBAD_AUTH`.
Accounts created on the private network don't exist on mainnet. Running the private network adds no risk.

**Testnet and mainnet history** are used only to mine patterns that already happened there, and as an optional
cross-check that a generated pattern also occurs on a public network.

**Today's evidence.** The generator in the evidence repo (`corpus/gen/`, Go, run in a container) produced its four
generated entries on testnet, and also runs against a local quickstart network. Its export step is still
testnet-only. Exporting from the private network, the multi-validator topology and the config upgrades are
Deliverable 1 work. The sample entries will be regenerated on the private network then.

A regenerated entry has a new tx hash, so regeneration is checked on invariants: the operation, the results, the
pattern's decoded values, and core's verdicts on the probes.

## 6. Replay harness

**Input.** The harness writes corpus ledgers into a local S3 (SeaweedFS) in the Galexie data-lake layout, including
`.config.json`, with one ledger per file. wallet-backend's `datastore` backend reads this layout, and so does
anything built on go-stellar-sdk's `BufferedStorageBackend`. A mock RPC `getLedgers` endpoint is a later adapter
input, not part of the first release.

**One entry per run.** Corpus entries are single ledgers from different networks and passphrases, so each entry runs
in a fresh, isolated indexer instance: its own database, its own data-lake bucket, the entry's network passphrase,
and only that ledger. State from earlier ledgers that the indexer needs is seeded through the adapter. Runs are
independent, so CI runs them in parallel.

**Adapter interface.**

```go
type Adapter interface {
    Start(ctx context.Context, run RunConfig) error                    // fresh indexer: passphrase, bucket, DB
    Ingest(ctx context.Context, ledger uint32) error                   // run it over the entry's ledger
    Observe(ctx context.Context, e corpus.Entry) (Observation, error)  // read back what it stored
    Stop(ctx context.Context) error
}

// Observation is a typed projection of what the indexer stored, compared field by field with the manifest.
type Observation struct {
    Transactions  map[string]TxObservation // by tx hash, for every target and control transaction
}
type TxObservation struct {
    Stored        bool
    Participants  []string                 // as strkeys, decoded by the harness, not by the indexer
    StateChanges  []StateChange            // kind, account, asset, signer, …
    Addresses     []string                 // every address the indexer stored for this tx, as strkeys
}
```

Each adapter maps its indexer's tables onto `Observation`. That mapping is the part a new indexer has to write.

**Control transactions.** Every entry ledger contains at least one plain control transaction whose expected values
are known. Mined ledgers almost always have several; the generator adds one to each generated ledger.

**Verdicts:**
- **pass:** every target is stored with the expected values;
- **mishandled:** a target is stored, but values are missing or wrong;
- **dropped:** the control is stored and a target is not. It doesn't matter whether the indexer logged anything:
  this is how silent drops are caught;
- **error:** the control isn't stored either, so the run itself failed (indexer didn't start, wrong config, data lake
  unreachable). The run is repeated and never filed.

Exit codes and logs are recorded for the findings report but never decide the verdict (§2.3). The evidence repo's
`sighting-729/repro.sh` already uses the ledger's other transactions as the control. It also checks the #729 error
in the log, which is stricter than this rule needs.

**Reference adapter: wallet-backend.** Already prototyped in `sighting-729/`. It:
- builds wallet-backend at any commit in a Go container;
- migrates a fresh TimescaleDB;
- runs `ingest` in backfill mode against the local data lake;
- queries the stored transactions and state changes;
- decodes stored addresses back to strkeys with its own code, independent of wallet-backend.

Two wallet-backend quirks the adapter handles, both found while building the evidence:
- Backfill on an empty database ingests nothing, because it only fills gaps below the latest ingested ledger. The
  adapter seeds one clearly marked placeholder row above the range.
- Backfill exits 0 on a failed batch.

**Memory.** Entries stream one ledger at a time. CI runs the harness under a fixed memory cap (512 MiB) over a corpus
larger than the cap, and fails if memory grows without bound. Unbounded growth is itself one of the failures under
test.

**Acceptance.** The reference adapter reproduces three wallet-backend issues on their pre-fix commits and passes on
the fixed ones:

| Issue | Pre-fix → fixed | Entry |
| --- | --- | --- |
| #729 (CAP-40 signed-payload signer) | `2a0a84ea` → `2c873353` | `cap0040-signed-payload-signer-01`. Already `dropped` → `pass` in the evidence repo. |
| #731 (SAC trustlines) | parent of PR #734 → `c152783c` (#734) | the CAP-73 entry |
| #716 (muxed addresses) | `f8e5786d` → `bb0b162b` (PR #753, "reduce a Soroban operation's source to its base account") | the muxed `ExtendFootprintTtl` / `RestoreFootprint` source entry |

## 7. SDK conformance runner

**What runs, per language:**

| Layer | JavaScript | Go | Rust |
| --- | --- | --- | --- |
| XDR | js-stellar-sdk (js-xdr) | go-stellar-sdk `xdr` | rs-stellar-xdr |
| strkey | js-stellar-sdk | go-stellar-sdk `strkey` | stellar-strkey |
| transaction | js-stellar-sdk `TransactionBuilder` | go-stellar-sdk `txnbuild` | n/a (no transaction builder) |
| domain helpers | `Asset.compare`, `LiquidityPoolAsset`, `scValToNative`, … | equivalents in go-stellar-sdk | soroban-sdk types where they apply (e.g. `MuxedAddress`) |

Each SDK runs in its own pinned container and reads only corpus files, input vectors and the manifest. For every
entry, each SDK emits the same JSON projection of what it decoded (hash, operations, addresses as strkeys, pattern
values). The runner compares those projections with the manifest and with each other. Checks per entry:

1. **XDR layer:** decode, then re-encode to the original bytes.
2. **Transaction layer:** parse the envelope with the SDK's high-level API, and compare the hash and pattern values
   with the manifest.
3. **Domain layer:** the SDK's own helpers on the decoded values.
4. **Ledger-meta layer:** decode the full `LedgerCloseMetaBatch`. Reported separately: meta support often lags
   transaction support.

**SDK input vectors.** Some SDK bugs can't be triggered by any ledger, because they are about input the SDK accepts
from its user. Examples: `MuxedAccount("0x10")`, `" 16 "`, offer IDs above 2^53 (#1785), over-limit vector lengths
(#581, #598), a non-address ScVal passed to `MuxedAddress` (#2099), and malformed strings (#1823, js-xdr #165). For
these the runner has a second, small vector set: each vector is an input and the result every SDK must give, either a
specific value or an error. Vectors are stored and versioned with the corpus, but kept separate from it (§2.2).

**Output.** The output is a divergence matrix: entry or vector × SDK × layer, with n/a cells where a layer doesn't
exist. When one SDK diverges, the runner drafts sibling issues for every affected SDK. A person triages them and
files them through the disclosure rules in §12, so halting defects are never published automatically. Fixes have not
always crossed SDKs: the Go SDK had already fixed the issuer-ordering bug when JS still had it.

**Acceptance.** The runner reproduces js-stellar-sdk #1766, #1785 and #1789 on pre-fix tags. #1766 and #1789 come
from corpus entries. #1785 comes from input vectors. The evidence repo's first version (JavaScript only, generic
checks over all five entries and four releases) already reproduces two of them:
- #1766: `mishandled` on 17.2.0, `pass` from 17.2.1;
- #1789: `mishandled` on 17.2.0 and 17.2.1 (`scValToNative` keeps 1 of 3 map entries, with no error), `pass` from
  17.3.0.

CI runs it on every push.

## 8. Linter (Go)

**What it is.** A static-analysis tool, in the sense of `go vet`, not a code formatter. It reads the source code of a
Go indexer without running it and reports three dangerous patterns in how the code handles ledger data:
- values stellar-core does not validate, used as if they were trusted;
- recursive parsing with no depth or size limit;
- participants taken from the transaction envelope instead of the ledger meta.

The linter and the replay harness catch different things. The harness finds a bug only when the corpus has an input
that triggers it. The linter finds the risky pattern in code before any such input has appeared on the network, and
in indexers the harness has no adapter for.

The linter is built on `golang.org/x/tools/go/analysis` and runs as a standalone binary and as a golangci-lint
plugin. We target Go because wallet-backend, stellar-etl and most indexers built on go-stellar-sdk are Go. It has
three rules:

| Rule | Source | Sink | Accepted as a check | Seeded from |
| --- | --- | --- | --- | --- |
| `XDRL001` unvalidated field trusted | reads of go-stellar-sdk `xdr` fields that the manifest's `core_validation` records mark `validated: false` (memo, Soroban auth trees, muxed IDs, event topics) | database writes and keys, identity maps, participant sets | a call to a configured validator function, or a comparison against a value derived from the meta (e.g. emitter == the asset's SAC contract ID) | asset identity read from an event topic without checking that the emitter is the asset's SAC |
| `XDRL002` missing depth or size cap | functions that recurse, directly or indirectly, over `ScVal`, `SorobanAuthorizedInvocation` and other recursive XDR types, and loops over XDR vectors | — | a depth parameter compared with a constant on every recursive path; a length check before the loop | wallet-backend's unbounded authorization trees |
| `XDRL003` participants from the envelope | functions that build an affected-account or participant set | — | the set also reads ledger-entry changes from the meta, including fee processing. Envelope sources (tx and op source) are allowed only next to it, not instead of it. | wrong factory deployer stored |

Every rule ships with seeded violations re-created in Go from the bugs in the table: our own production bugs for
rules 1 and 3, wallet-backend's for rule 2.

**Acceptance.** The linter flags every seeded violation and reports nothing on current wallet-backend. If it finds a
real issue in current wallet-backend, that is filed upstream as a finding (§12) and recorded in a baseline file, so
the clean run stays meaningful.

## 9. Indexer-hardening guide

The guide is written for developers.stellar.org. It follows the RFP's fixed outline (items 1–4 and 6) and adds one
section from our own experience (item 5):
1. which transaction fields stellar-core validates (signatures, sequence numbers, fees, time bounds) and which it
   passes through (memos, Soroban auth trees, muxed IDs). This is a field-by-field table over the fields of
   `TransactionEnvelope`, its operations and its Soroban data, giving the stage (validation, apply or Soroban host)
   and the evidence, checked against the manifest;
2. recommended depth and size caps, each derived from the XDR and Soroban host limits it protects against;
3. deriving participants from the meta, with factory deployments as a worked example;
4. muxed and signed-payload handling, including SEP-23 strkey forms and column sizes (`M…` 69 chars, `B…` 58, `P…`
   up to 165);
5. surviving protocol upgrades: pin tracking, and decoding a new protocol's ledger before the vote. This is the
   watcher we run in production, which opens an issue whenever our pinned `stellar-xdr` lags the protocol core
   already supports;
6. a self-audit checklist mirroring the three linter rules, for indexers in other languages.

Publication requires review by a stellar-core or platform engineer. We request that review as soon as the draft,
with the field table, exists, and address every comment. The guide is delivered ready to publish, as a pull request
to the Stellar developer docs; merging it is the docs maintainers' call.

## 10. CI, release and adoption

- Every tool (generator, harness, conformance runner, linter) has its own test suite.
- Every pull request in the tools' repos runs those tests and the full corpus, offline:
  - round-trip and manifest freshness;
  - schema and the second-decoder cross-check;
  - regeneration under both passphrases;
  - the harness against wallet-backend, under the memory cap;
  - the conformance runner against all three SDKs.
  The CI log reports the harness run time.
- A **GitHub Action** lets any indexer or SDK run the corpus in its own CI. It is the cheapest way for a third-party
  indexer to adopt the kit.
- **Adoption starts with SDF's own pipeline:** we open a pull request adding the corpus check to wallet-backend's CI.
- Releases are tagged; corpus releases are versioned by the newest protocol covered.

## 11. License, infrastructure and scope

**License.** Apache-2.0 for all code and the corpus.

**Infrastructure and user tracking.** There is no hosted service: everything runs locally or in CI, in Docker (a
local S3, Postgres for the indexer under test, a private stellar-core network, Galexie, pinned SDK containers).
Everything is built on the current stable Stellar stack (stellar-xdr 30, current js-stellar-sdk and go-stellar-sdk
releases) and bumped with each protocol release. There is no telemetry and no user tracking.

**Scope limits.**
- The linter covers Go only; other languages use the guide's checklist.
- There is one reference adapter (wallet-backend); others can be added through the documented interface.
- The Galexie data-lake input comes first; a mock RPC `getLedgers` input is later work.
- Findings are filed upstream with a reproducing entry, not fixed by us.
- Coverage is measured on arms that can occur in a closed ledger. Arms core rejects before a ledger are recorded as
  negative probes, not corpus entries.
- Sightings that are not ledger shapes are out of scope for the corpus (sightings table, §4.4).

## 12. Findings and disclosure

**Findings report.** One row per finding:
- the issue link, or a private-advisory reference;
- the corpus entry or input vector;
- severity:
  - **critical:** halts ingestion;
  - **high:** data loss or corruption;
  - **medium:** a decoding divergence;
  - **low:** anything else;
- the affected CAP and component.

Every failure maps to a row. A private advisory counts as filed.

**Disclosure.** Ingestion-halting inputs are denial-of-service vectors against production indexers. Critical and
high findings are reported privately first, to SDF's security disclosure channel and the affected maintainers. The
public issue and the corpus entry follow once a fix is released, and publication is tracked under maintenance if it
falls after delivery. Medium and low findings are filed publicly right away.

## 13. Maintenance and protocol upgrades

Our team maintains the kit for 12 months after the production release, with one named maintainer:
- **Each new CAP:** corpus entries for every CAP that ships in that window, including the first protocol upgrade
  after delivery.
- **Each protocol on testnet:** the harness and conformance runner run over the new protocol's ledgers before the
  mainnet vote, with findings filed upstream.
- **Issues:** triaged within 10 business days.

Findings made while building it:
- stellar-core rejects a muxed source or a memo on `InvokeHostFunction` from protocol 25. `ExtendFootprintTtl` and
