# XDR/CAP-Coverage Audit Tool and Indexer-Hardening Guide: Technical Architecture

Technical design for our response to the SCF RFP "XDR/CAP-Coverage Audit Tool and Indexer-Hardening Guide". This
document can be read on its own, without the grant application. Working evidence for every part described here is
public at [rumblefishdev/xdr-corpus-evidence](https://github.com/rumblefishdev/xdr-corpus-evidence).

## 1. Summary

Every application that reads the Stellar ledger decodes XDR. Shapes that are rare but valid crash these readers or,
worse, are silently dropped, because nobody tests them. We build one shared test kit for them:

| Component | What it does | Who uses it |
| --- | --- | --- |
| **Corpus** | rare but valid ledger and transaction shapes, tagged by CAP and protocol, with the values a correct reader must decode. Entries are emitted by stellar-core; hand-built bytes are allowed only as a marked fallback (§2.2). | everyone below |
| **SDK input vectors** | invalid inputs an SDK may receive from its user (malformed strings, over-limit lengths, out-of-range numbers), each with the result the SDK must give | SDK maintainers |
| **Generator** | reproducibly produces the corpus entries that can't be mined from history, offline, on a private stellar-core | corpus maintainers |
| **Replay harness** | delivers the corpus to an indexer through the Galexie data-lake layout and reports *pass / mishandled / dropped / halted* per entry, or *error* when the run itself failed | indexer authors (wallet-backend, stellar-etl, third parties) |
| **Conformance runner** | runs the corpus and the input vectors through the JS, Go and Rust SDKs and reports every divergence from the network or between SDKs | SDK maintainers |
| **Linter** | flags the three ingestion mistakes in Go indexer source | Go indexer authors |
| **Indexer-hardening guide** | which fields core validates, caps, participants-from-meta, muxed and signed-payload handling, checklist; delivered ready to publish on developers.stellar.org | every indexer author, any language |

## 2. Design principles

These come from running two production indexers, the
[Soroban Block Explorer](https://github.com/rumblefishdev/soroban-block-explorer) and the
[Prices API](https://github.com/rumblefishdev/stellar-prices-api), and from building the evidence for this proposal.

1. **Expected values come from the network, never from a reader.** A reader's output can share the mistake of the
   code under test, so it can't be the reference. Expected values are what stellar-core itself recorded in the
   ledger: transaction and operation results, ledger-entry changes in the meta (including fee processing), and
   contract IDs as they appear in the meta. Values that are conventions rather than ledger data, such as event IDs,
   are derived from the event's position in the meta, in the format of a pinned stellar-rpc version. That includes
   its special cursors for CAP-67's transaction-level events (before all transactions, after a transaction, after
   all transactions). No expected value depends on querying a reader such as Horizon or stellar-rpc.
2. **Corpus bytes are emitted by stellar-core.**
   - Entries are mined from network history, generated by submitting real transactions, or taken from stellar-core's
     own test goldens.
   - Hand-built bytes are allowed only for valid variants no network or core test has emitted, and they are marked
     `synthetic`.
   - A pattern core would reject is never in the corpus as valid input. It is recorded as a negative probe.
   - Invalid input that only an SDK's user can produce (malformed strings, over-limit lengths) lives in the separate
     SDK input vectors (§7), never in the corpus.
3. **Verdicts come from stored data and from what the harness itself observed, never from exit codes.**
   - **Failure:** in our evidence run, wallet-backend's backfill logged the failed batch and **exited 0** after losing
     a whole ledger.
   - **Failure:** in our own pipeline, a single unwritable ledger stalled ingestion for 19 minutes, and the failure was
     reported as success.
   - **Rule:** the harness inspects what the indexer stored. It also serves the data lake itself, so it sees whether
     the indexer fetched the ledger. An indexer that fetched a ledger and stored nothing from it **halted** on it.
     That is the most critical finding, never an inconclusive one (§6).
4. **A clean build proves nothing about a protocol upgrade.**
   - **Failure:** protocol 27 froze both our indexers; the Prices API stalled for six days with no alarm. In protocols
     28 and 30 the new variant sits in a type nested inside the ledger header. Code compiles, then fails on the first
     ledger that carries the variant, hours or days after activation.
   - **Rule:** only decoding such a ledger through the production code path proves support. The corpus holds such
     ledgers, and the harness drives that code path.
5. **The corpus is language-neutral.** It is XDR files plus a JSON manifest. Any pipeline can read it without our
   code.

## 3. Architecture

```
 network history ──► mined entries ─────────┐
 generator ────────► generated entries ─────┤   corpus: XDR files + manifest.json
 (private core)      (testnet / mainnet     ├─► per-CAP coverage report
                      passphrase)           │   manifest = fresh decode (CI)
 stellar-core ─────► golden entries ────────┤
 hand-built ───────► synthetic entries ─────┘
                                │
       ┌────────────────────────┼─────────────────────────────┐
       ▼                        ▼                             ▼
 replay harness           conformance runner            guide field table
 local S3 (Galexie),      js-stellar-sdk (Node)         + checklist
 local RPC + archive      go-stellar-sdk (Go)           + linter rule IDs
 stubs                    rs-stellar-xdr, stellar-strkey,
 → adapter per indexer    soroban-sdk (Rust)
 → verdict per entry      + SDK input vectors
       │                  → divergence matrix
       └──────────┬─────────────┘
                  ▼
        findings report → triage → issues filed upstream
                                   (halting bugs: private disclosure first)
```

Everything in CI runs offline, meaning with no access to any Stellar network. It runs in Docker, with pinned and
pre-pulled images and packages, and needs no keys or funds. Mining from testnet or mainnet history and optional
public-network cross-checks run outside CI.

## 4. Corpus

### 4.1 Entry layout

Already implemented in the evidence repo (`corpus/entries/cap-00NN/<id>/`):

| File | Content |
| --- | --- |
| `FF…--<ledger>.xdr.zst` | the ledger exactly as Galexie wrote it to the data lake, under Galexie's object name (`FF…` = 0xFFFFFFFF − ledger): zstd-compressed `LedgerCloseMetaBatch`. This captured file is canonical (sha256). It is never re-sorted, because some ledger-entry changes must stay in core's order for downstream consumers. |
| `ledger-<n>.LedgerCloseMetaBatch.xdr` | the same, decompressed |
| `tx-<first 16 hex of hash>.TransactionEnvelope.xdr` | the target transaction alone, extracted from the ledger file. An SDK release that predates the ledger's protocol can still be tested on the pattern itself. For example, js-stellar-sdk 17.2.x can't decode protocol-30 ledger meta; support arrived in 17.3.0. |
| `generation.json` | generated entries only (mined entries have none): public keys, every submission and stellar-core's answer to it, including the rejected *negative probes* |

Golden entries (§4.3) keep stellar-core's own file as canonical: a stream of length-prefixed `LedgerCloseMeta`
records, including the ledgers before the target that set up its state. A converter writes the same ledgers as
Galexie `LedgerCloseMetaBatch` objects for the harness and the runner; the harness ingests the setup ledgers before
the target (§6).

### 4.2 Manifest

`manifest.json` is **generated** from the files by a tool, and CI fails if it differs from a fresh decode. The only
hand-written inputs are:
- which transactions and operations an entry is about (its target or targets);
- the CAP and SEP tags;
- the protocol a CAP introduced;
- each pattern's invariants (the fields that must not change when the entry is regenerated);
- the per-field `core_validation` records. Each record is backed by a negative probe, an accepted edge value, or a
  stellar-core source reference pinned to a commit and line;
- issue links.

The table below is the **target schema** for the release. The draft schema in the evidence repo
(`corpus/manifest.schema.json`, JSON Schema 2020-12) already has most of it, including `accepted` and per-field
`core_validation[]` records with their evidence. It differs mainly in these places, all reconciled in Deliverable 1:
- `targets[]`, `pattern_targets[]` and the `decoded`/`network` provenance marks are not there yet;
- `source.kind` still has a `local` value and no `golden` value; `network` has no `golden` value;
- `check_lcm_golden` is a path string (null in all five entries), not the record described here;
- it has draft-only fields (e.g. generator and generation-record references) that the release folds into `source`.

| Field | Meaning |
| --- | --- |
| `id`, `title`, `cap[]`, `sep[]` | entry identity, title and tags. A pattern that predates the CAP process carries `pre-CAP` with the protocol it dates from, so every entry has a CAP tag. |
| `pattern` | `{ id, description }`. The pattern id selects the typed `extra` block and its invariants. |
| `protocol.introduced_in` / `protocol.ledger` | where the pattern can first occur / protocol of the captured ledger |
| `network`, `network_passphrase` | `pubnet`, `testnet`, `futurenet`, `local`, `golden` or `other`, with the exact passphrase. Private-network entries are `local` and carry the passphrase they were generated with. Golden entries carry stellar-core's test passphrase. |
| `source.kind` | `mined` / `generated` (on any network, including the private one) / `golden` / `handcrafted` |
| `synthetic` | the schema enforces `synthetic == (kind == handcrafted)` |
| `files[]` | path, XDR type, encoding, layout, sha256, `derived_from` |
| `targets[]` | the target transactions (one for most entries; one per result code in a sweep entry, §4.4), each with its own expected values |
| `pattern_targets[]` | the coverage targets (union arms, optional fields) this entry claims as its pattern, and so carries expected values for |
| `accepted` | core accepted the target transaction into a ledger |
| `core_validation[]` | one record per transaction field the entry exercises: `{ field, validated, stage, evidence_kind, evidence }`. `stage` is where core checks the field: `validation`, `apply` or `host` (Soroban host checks such as auth). `evidence_kind` is `rejected_probe` (proves the field *is* validated), `accepted_probe` (an edge value core accepted, which proves it *is not*) or `source_ref`. |
| `negative_probes[]` | nearby invalid variants and core's rejection. Their `stage` is where the variant was rejected (`simulation`, `submission`, `apply`); this vocabulary is separate from `core_validation.stage`. |
| `expected` | fields shared by every target: ledger, tx, operation, results, sources. Each field is marked `decoded` (from rs-stellar-xdr) or `network` (cross-checked by a second decoder, §4.3). |
| `extra` | the pattern's own decoded values, e.g. signer key, muxed ID, pool ID, asset order |
| `roundtrip` | byte-exact decode/encode result and the tool version |
| `check_lcm_golden` | for golden entries and for patterns a golden also covers: the stellar-core commit, test name and section |
| `related[]` | sightings and issues the entry reproduces |

### 4.3 Validation

| Check | Establishes | Runs |
| --- | --- | --- |
| sha256 of every file equals the manifest | the files are the captured ones | CI, every pull request |
| decode → encode is byte-exact with rs-stellar-xdr | a reference decoder reads and writes the entry losslessly | CI, every pull request |
| agreement with stellar-core's `--check-lcm` goldens (method below), against goldens vendored at the pinned stellar-core commit | the corpus matches what core itself treats as correct | CI, every pull request (no stellar-core build in CI) |
| file consistency: the `.zst` decompresses to the `.xdr`; envelope hash = tx hash; every envelope maps to a result | the entry's files agree with each other | CI, every pull request |
| manifest = fresh decode | no expected value was typed or edited by hand | CI, every pull request |
| `network` fields agree between rs-stellar-xdr and a second decoder (go-stellar-sdk's xdr) | network-recorded expected values don't depend on one decoder | CI, every pull request |
| manifest validates against the schema | the schema is enforceable | CI, every pull request |
| every field in the guide's table has at least one `core_validation` record (a probe, or a pinned stellar-core source reference), and all records agree with the table | the guide and the corpus can't drift apart, and a field with no evidence shows up as a gap | CI, every pull request |
| regenerating a generated entry, offline, keeps the same pattern and core verdicts | the generator reliably produces the pattern | CI: entries whose generator changed, on every pull request; all entries under both passphrases, at each release |

**Agreement with stellar-core's goldens.** stellar-core records the LedgerCloseMeta its own unit tests produce
(`test-lcm-current/`, `test-lcm-next/`) and compares new runs against them with `--check-lcm`. Before writing a
golden, core zeroes the non-deterministic diagnostic events but keeps the original order of entries. When comparing,
it sorts copies of both sides. Goldens come from core's own test scenarios, with their own accounts and a test
passphrase, so a ledger we mine or generate is never byte-for-byte comparable with one. We therefore do two things:
1. **Golden entries.** We import stellar-core goldens as corpus entries (`source.kind = golden`), taken at a pinned
   stellar-core commit. The release contains at least one. The first candidates:
   - `test-lcm-current/FrozenLedgerKeysTests/`, for the CAP-77 freeze patterns, which are otherwise hard to produce;
   - the CAP-83 empty-transaction-set ledger that stellar-core's HerderTests captured
     (`test-lcm/HerderTests/370dd5e0af5cfa8d.xdr`, added with CAP-83 in commit `6bd15f5f02`). Core no longer
     captures this test on master, so this is a **historical golden**: imported from that commit and not re-checked.
   When we move to the next pinned stellar-core release, each golden entry whose test core still captures is
   compared with core's golden for the same test, using core's own comparison (diagnostics zeroed, sorted copies).
   A difference means core's output for that scenario changed. The entry is then reviewed and updated, and indexers
   are tested against both versions.
2. **Structural agreement for other entries.** A mined or generated entry is matched to a golden when their
   `pattern_targets[]` overlap. For each overlapping coverage target, the two must agree on structure, not on values:
   - the same discriminant path from the ledger root to the arm;
   - the same result codes for the operations that produce it;
   - the same ledger-entry change kinds (created, updated, removed, restored, state) per ledger-entry type.
   Accounts, amounts and hashes differ by design and are not compared. An entry whose `pattern_targets[]` overlap no
   golden is marked "no published golden"; the RFP asks for agreement only where goldens are published.

The same comparison (diagnostics zeroed, sorted copies, never applied to the canonical file) is how we check that a
re-export of a ledger equals its captured file.

**Checking the Rust SDK.** The manifest's decoded values come from rs-stellar-xdr, so checking the Rust SDK against
them alone would be circular. Expected fields marked `network` (result codes, ledger-entry changes, event positions,
contract IDs as recorded in the meta) are decoded a second time by go-stellar-sdk's xdr package, and CI requires the
two decoders to agree. Both libraries are generated from the same `.x` files, so this catches codec bugs in either
library, not a misreading of the XDR spec itself. The meaning of those fields is anchored by what core recorded
(results and ledger-entry changes) and by the goldens. Every SDK, Rust included, is then checked against the
cross-checked fields.

### 4.4 Coverage plan

**Sizing.** Counting CAPs says little about coverage. One CAP can add several shapes, and many add none that a reader
ever sees. Our coverage tool (prototype: `corpus/tools/coverage-targets.py` in the evidence repo) counts from the
XDR itself. It parses stellar-xdr at every protocol tag from v19 to v30 and lists every union arm and optional field
reachable from `LedgerCloseMetaBatch`. At protocol 30 that is **499 union arms and 28 optional fields** (56 optional
targets, present and absent). It dates each arm to the protocol that added it, and tags it with the CAP that added
it. CAP tags come from the stellar-xdr history, with a hand-checked override table where commit messages name the
wrong CAP or none. Today 16 of the 38 arms added in protocols 21-30 still have no tag. In Deliverable 1 each of those
38 arms gets a CAP tag or an explicit "no CAP" with a reason (e.g. a numbered `v0`/`v1` extension slot added for a
protocol release).

Findings from the five sample entries:
- they already contain 123 arms (25%), mostly through incidental content of their ledgers, not their targets;
- of the 376 arms not yet contained, about 230 are operation and transaction result codes. Failed operations land in
  ledgers and can be generated;
  some transaction-level codes are rejected before a ledger and belong in `negative_probes`;
- 27 of the 38 arms added in protocols 21-30 are not yet contained. That is the protocol-upgrade class of failure
  (§2.4).

**Two coverage numbers.** An arm can be in an entry only by accident (some other transaction in the same ledger), so
we report two numbers:
- **pattern coverage:** arms an entry claims in `pattern_targets[]`, with expected values checked by every tool;
- **incidental coverage:** arms that appear anywhere in an entry's files.

**Coverage report, published in Deliverable 1.** The report lists every arm at protocol 30 with the entries that
contain it, by pattern and incidentally, and is regenerated in CI. Arm coverage is a measurement, not an acceptance
target. The 38 arms added in protocols 21-30 are classified, best effort, **at protocol 30**, as *in
ledgers*, *rejected by core* or *not in meta*, and each one excluded from *in ledgers* carries its evidence (a
negative probe or a pinned stellar-core source reference). Arms that occur only in older history (e.g. inflation
results, `LedgerCloseMeta` v0) are mined where history has them and marked *historical*.

Release targets:
- every ledger pattern RFP §3 names, and every §7 sighting the table below maps to an entry, has one;
- **every CAP that added an arm in protocols 21-30, and every CAP the RFP names**, has at least one pattern entry, or
  a documented "no reader-visible shape" with its evidence. The empty-transaction-set CAPs count through the CAP-83
  golden entry (§4.3);
- the share of the 38 protocol 21-30 arms covered by entries is reported, not targeted.

## 5. Generator

**Main path: a private, isolated stellar-core.** The generator runs offline, against a private stellar-core network
with its own local history archive and its own stellar-rpc, configured with either the testnet or the mainnet
passphrase. So generation is reproducible for both passphrases, needs no keys or funds, and runs in CI. Core itself
signs, hashes and emits these ledgers, so the entries are core-emitted, not synthetic.

**Isolation.** The private network runs on an internal-only Docker network with no route to the internet. Its
validators have empty `KNOWN_PEERS` and `PREFERRED_PEERS`. With the mainnet passphrase, a misconfigured node could
otherwise pass a mainnet peer's network-ID handshake, so this isolation is required, not optional.

**Settings that shapes depend on.** Soroban limits (transaction size, instructions, entry sizes) bound "maximum
length" and practical nesting depth. On the private network they are set to mainnet's values through a
`ConfigUpgradeSet` (Deliverable 3) before generating the maximum-length entries, and recorded in the manifest. Network
settings that don't affect a pattern's shape (validator keys, fees) stay the private network's own.

**Protocol pinning.** The private network starts at the protocol a pattern needs and is upgraded through the usual
ledger upgrades. For example, the first ledger carrying the protocol-28 header variant is produced by upgrading the
network from protocol 27 to 28. The empty-transaction-set header arms are the exception: a single validator can't
produce them, and they come from the CAP-83 golden (§4.3).

Topologies:
- **one validator** for every pattern in this award.
- **Several validators** would be needed for patterns that only arise from consensus. The one we know of is the
  CAP-83 empty transaction set, whose delivered entry is the historical stellar-core golden captured with CAP-83
  (§4.3). Generating one on a multi-validator network (one validator not receiving the proposed transaction set in
  time) is planned after 1.0, not part of this award.

For each pattern the generator:
1. funds fresh accounts from the private network's genesis root account;
2. builds the transactions with go-stellar-sdk and submits them through the private network's stellar-rpc;
3. submits the nearby invalid variants first and records core's rejection of each.

Some patterns need a network configuration change: the Soroban limits above, the new `ConfigSettingEntry` arms, and
the CAP-77 frozen keys (all Deliverable 3). For those, the generator uploads a `ConfigUpgradeSet` and arms the upgrade
on the private network's validators, the same way the public network upgrades its settings.

Galexie then exports the target ledger from the local archive, and the manifest tool fills in the entry. The private
network uses accelerated test settings (short ledger close times and checkpoint interval, as `stellar/quickstart
--local` does), so the archive checkpoint arrives quickly.

**Safety with the mainnet passphrase.** stellar-core derives the genesis root key from the passphrase, so the private
network's root key is the same as mainnet's root key, which anyone can already derive. Its secret key is therefore
already public. Envelopes generated with the mainnet passphrase carry signatures that are valid for mainnet, but
their source accounts exist only on the private network, so submitting one to mainnet fails: the source account
doesn't exist. Generator keys are fresh per run and never reused. Together with the isolation above, running the
private network adds no risk.

**Testnet and mainnet history** are used only to mine patterns that already happened there, and as an optional
cross-check, outside CI, that a generated pattern also occurs on a public network.

**Today's evidence.** The generator in the evidence repo (`corpus/gen/`, Go, run in a container) produced its four
generated entries on testnet, and also runs against a local quickstart network. Its export step is still
testnet-only. Exporting from the private network and the golden import are Deliverable 1 work. The sample entries
will be regenerated on the private network then.

A regenerated entry has a new tx hash, so regeneration is checked on invariants: the operation, the results, the
pattern's decoded values, and core's verdicts on the probes.

## 6. Replay harness

**Infrastructure per run.** The harness gives the indexer under test everything it would otherwise fetch from a
network, from local sources:
- a local S3 (SeaweedFS) holding the entry's ledger in the Galexie data-lake layout, including `.config.json`, with
  one ledger per file. wallet-backend's `datastore` backend reads this layout, and so does anything built on
  go-stellar-sdk's `BufferedStorageBackend`;
- a **local stellar-rpc stub**. wallet-backend requires `RPC_URL` even with the datastore backend: for its health
  check and the latest-ledger query, and for contract (token) metadata through ledger-entry lookups. The stub serves
  these from the entry's own ledger state, so SAC and SEP-41 metadata is deterministic and offline;
- a **local history-archive stub** for indexers that connect to an archive at start-up;
- a fresh database.

A mock RPC `getLedgers` endpoint as a *ledger source* is a later adapter input, not part of the first release.

**One entry per run.** Corpus entries are single ledgers from different networks and passphrases, so each entry runs
in a fresh, isolated indexer instance: its own database, its own bucket, the entry's network passphrase, and only
that ledger. State from earlier ledgers that the indexer needs (accounts, trustlines, contract instances) is seeded
through the adapter's `Seed` step, from the entry's own ledger-entry changes. Golden entries are the exception: their
setup ledgers are ingested before the target ledger, as core produced them. Runs are independent, so CI runs them in
parallel.

**Adapter interface.**

```go
type Adapter interface {
    Start(ctx context.Context, run RunConfig) error                    // fresh indexer: passphrase, bucket, RPC stub, DB
    Seed(ctx context.Context, state []xdr.LedgerEntry) error           // pre-existing state the entry's ledger needs
    Ingest(ctx context.Context, ledger uint32) error                   // run it over the entry's ledger
    Observe(ctx context.Context, e corpus.Entry) (Observation, error)  // read back what it stored
    Stop(ctx context.Context) error
}

// Observation is a typed projection of what the indexer stored.
type Observation struct {
    Transactions map[string]TxObservation // by tx hash, for every transaction of the ledger
}
type TxObservation struct {
    Stored       bool
    Operations   []OperationObservation   // type, source, result
    Participants []string                 // as strkeys, decoded by the harness, not by the indexer
    StateChanges []StateChange            // kind, account, asset, signer, balance before/after
    Events       []EventObservation       // contract, topics, data, and the event ID the indexer assigned
    Addresses    []string                 // every address the indexer stored for this tx, as strkeys
}
```

**The reference projection.** The harness computes the same `Observation` shape from the manifest, as what a correct
indexer should store:
- participants are the accounts and contracts whose ledger entries change in the meta (including fee processing),
  plus the transaction and operation sources;
- state changes are the meta's ledger-entry changes, by kind;
- events are the meta's contract events, without diagnostic events;
- muxed addresses: participants and stored addresses are compared as base accounts (`M…` reduces to its `G…`). The
  muxed ID is checked only where the adapter declares that its indexer stores it.
Each adapter maps its indexer's tables onto `Observation`. It also declares which fields its indexer doesn't store
at all, which address kinds it deliberately skips (listed in the findings report, never silent), and which
transactions it is expected to store (all of them for wallet-backend; for example only those
touching tracked accounts for a filtering indexer). Undeclared fields are skipped rather than failed, and verdicts
consider only the expected transactions. That mapping is the part a new indexer has to write.

**Verdicts.** The harness serves the data lake, so its S3 access log shows whether the indexer fetched the entry's
ledger. That, plus a start-up health probe (process up, database migrated), separates indexer failures from harness
failures:
- **pass:** every expected transaction of the ledger is stored, and each target matches the reference projection;
- **mishandled:** a target is stored, but values are missing or wrong;
- **dropped:** other expected transactions of the ledger are stored, and a target is not. This is how silent drops are
  caught, with or without anything in the indexer's log;
- **halted:** the indexer fetched the ledger but stored none of its expected transactions, or it crashed, ran out of
  its memory limit or exceeded its time limit on that ledger. This is the ingestion-halt class (#729, #753), and it is
  always a finding, rated critical;
- **error:** the health probe failed or the indexer never fetched the ledger, so the harness itself failed. The run
  is repeated and never filed.

Exit codes and logs are recorded in the findings report as supporting evidence, but never decide the verdict (§2.3).
The evidence repo's `sighting-729/repro.sh` already reports `halted` for #729. Until the harness serves the data lake
itself, it uses the #729 error in the log as its proof that the indexer reached the ledger.

**Limits on the indexer under test.** Each entry runs with a per-entry memory limit (1 GiB) and time limit
(120 seconds) on the indexer's container. Exceeding either is a `halted` verdict with the cause recorded. This is how
the corpus tests for unbounded memory growth in the indexer, which the RFP names as one of the failures under test.
The harness itself streams one entry at a time and holds no corpus-sized state.

**Reducing a halt to a minimal entry.** A mined mainnet ledger can hold many target transactions. If
the indexer halts on one, the halt can't be attributed from the ledger alone. During triage we regenerate the
suspect targets as single-target ledgers on the private network and rerun them, so every finding has a minimal
reproducing entry, as the RFP requires.

**Reference adapter: wallet-backend.** Already prototyped in `sighting-729/`. It:
- builds wallet-backend at any commit in a Go container;
- migrates a fresh TimescaleDB;
- runs `ingest` in backfill mode against the local data lake and the RPC stub;
- queries the stored transactions and state changes;
- decodes stored addresses back to strkeys with its own code, independent of wallet-backend.

Two wallet-backend quirks the adapter handles, both found while building the evidence:
- Backfill on an empty database ingests nothing, because it only fills gaps below the latest ingested ledger. The
  adapter seeds one clearly marked placeholder row above the range.
- Backfill exits 0 on a failed batch.

The evidence repo still points `RPC_URL` at testnet and checks Horizon. Both move to the stub, and the Horizon check
moves to an optional job outside CI.

**Acceptance.** The reference adapter reproduces three wallet-backend issues on their pre-fix commits and passes on
the fixed ones:

| Issue | Pre-fix → fixed | Entry | Expected verdicts |
| --- | --- | --- | --- |
| #729 (CAP-40 signed-payload signer) | `2a0a84ea` → `2c873353` | `cap0040-signed-payload-signer-01` | `halted` → `pass` |
| #731 (SAC trustlines) | `764a4f5b` → `c152783c` (PR #734) | the CAP-73 entry | `mishandled` → `pass` |
| #716, Soroban operation-source producer | `f8e5786d` → `bb0b162b` (PR #753) | the muxed `ExtendFootprintTtl` / `RestoreFootprint` source entry | `halted` (duplicate primary key) → `pass` |

#716 itself was closed without a linked fix commit, and #753 fixed one of its three producers with a different
symptom at the pre-fix commit (a halt, not a truncation). That is why this pair is #716's acceptance pair. The

`InvokeHostFunction`, and #753's description states the same and describes the halt (duplicate primary key,
SQLSTATE 23505). We raise this substitution with SCF at kickoff.

## 7. SDK conformance runner

**What runs, per language:**

| Layer | JavaScript | Go | Rust |
| --- | --- | --- | --- |
| XDR | js-stellar-sdk (js-xdr) | go-stellar-sdk `xdr` | rs-stellar-xdr |
| strkey | js-stellar-sdk | go-stellar-sdk `strkey` | stellar-strkey |
| transaction | js-stellar-sdk `TransactionBuilder` | go-stellar-sdk `txnbuild` | n/a (no transaction builder) |
| domain helpers | `Asset.compare`, `LiquidityPoolAsset`, `scValToNative`, … | equivalents in go-stellar-sdk | soroban-sdk types where they apply (e.g. `MuxedAddress`) |

Each SDK runs in its own pinned container and reads only corpus files, input vectors and the manifest. For every
entry, each SDK emits the same JSON projection of what it decoded (hash, operations, addresses as strkeys, pattern
values). The runner compares those projections with the manifest and with each other. Checks per entry:

1. **XDR layer:** decode, then re-encode to the original bytes.
2. **Transaction layer:** parse the envelope with the SDK's high-level API, and compare the hash and pattern values
   with the manifest.
3. **Domain layer:** the SDK's own helpers on the decoded values.
4. **Ledger-meta layer:** decode the full `LedgerCloseMetaBatch`. Reported separately: meta support often lags
   transaction support.

**SDK input vectors.** Some SDK bugs can't be triggered by any ledger, because they are about input the SDK accepts
from its user, e.g. `MuxedAccount("0x10")`, `" 16 "` or `""` (#1785). For these the runner has a second, small
vector set: each vector is an input and the result every SDK must give, either a specific value or an error. Vectors
are stored and versioned with the corpus, but kept separate from it (§2.2). The #1785 vectors are part of acceptance.
Vectors for other sightings (#581/#598 over-limit lengths, #2099, #1823, js-xdr #165) are optional extras.

**Output.** The output is a divergence matrix: every entry and vector × JS, Go and Rust × layer, with n/a cells only
where a layer doesn't exist, each with its reason. When one SDK diverges, the runner drafts sibling issues for every
affected SDK, and a person files them through the disclosure rules in §12, so halting defects are never published
automatically. Fixes have not
always crossed SDKs: the Go SDK had already fixed the issuer-ordering bug when JS still had it.

**Acceptance.** The runner reproduces js-stellar-sdk #1766, #1785 and #1789 on pre-fix tags and passes on fixed
ones, and every entry round-trips through the XDR layer of all three SDKs. The other matrix cells are produced and
reported, not gated. #1766 and #1789 come from corpus entries; #1785 comes from input vectors. We checked #1785's
muxed-ID side by hand: js-stellar-sdk 17.2.1 accepts `MuxedAccount` IDs `"0x10"`, `" 16 "` and `""`, and 17.3.0
(with PR #1780) rejects all three. The evidence repo's first version (JavaScript only, generic checks over all five
entries and four releases) already reproduces the other two:
- #1766: `mishandled` on 17.2.0, `pass` from 17.2.1;
- #1789: `mishandled` on 17.2.0 and 17.2.1 (`scValToNative` keeps 1 of 3 map entries, with no error), `pass` from
  17.3.0.

CI runs it on every push.

## 8. Linter (Go)

**What it is.** A static-analysis tool, in the sense of `go vet`, not a code formatter. It reads the source code of a
Go indexer without running it and reports three dangerous patterns in how the code handles ledger data:
- values stellar-core does not validate, used as if they were trusted;
- recursive parsing with no depth or size limit;
- participants taken from the transaction envelope instead of the ledger meta.

The linter and the replay harness catch different things. The harness finds a bug only when the corpus has an input
that triggers it. The linter finds the risky pattern in code before any such input has appeared on the network, and
in indexers the harness has no adapter for.

The linter is built on `golang.org/x/tools/go/analysis` and runs as a standalone binary and as a golangci-lint
plugin. We target Go because wallet-backend, stellar-etl and most indexers built on go-stellar-sdk are Go. It has
three rules:

| Rule | Source | Sink | Accepted as a check | Seeded from |
| --- | --- | --- | --- | --- |
| `XDRL001` unvalidated value trusted | a fixed list of go-stellar-sdk `xdr` accessors. Transaction fields come from the `core_validation` records marked `validated: false` (memo, Soroban auth trees, muxed IDs). Host-emitted data (contract event topics and data, which any contract can emit) is a separate, explicitly listed group. | database keys and identity maps (asset, account, contract identity) | a call to a validator function named in the linter's config, or a comparison against a value derived from the meta (e.g. emitter == the asset's SAC contract ID) | our own: asset identity read from an event topic without checking that the emitter is the asset's SAC |
| `XDRL002` missing depth or size cap | functions that recurse, directly or indirectly, over `ScVal`, `SorobanAuthorizedInvocation` and other recursive XDR types, and loops over XDR vectors | — | a depth parameter compared with a constant on every recursive path; a length check before the loop | wallet-backend's unbounded authorization trees |
| `XDRL003` participants from the envelope | functions that build an affected-account or participant set, identified by a `//xdrlint:participants` annotation or by name patterns in the linter's config | — | the set also reads ledger-entry changes from the meta, including fee processing. Envelope sources (tx and op source) are allowed only next to it, not instead of it. | seeded violations written for this rule from the RFP's description; no production bug is cited |

Every rule ships with seeded violations in Go.

All three rules are intraprocedural: each looks within one function (plus the annotation or config that marks
validator and participant-building functions), not across call chains.

**Acceptance.** The linter flags every seeded violation, has its own test suite in CI, and reports no finding on
wallet-backend's latest release at the start of Deliverable 3 (commit pinned then) that hasn't been filed upstream. A
real issue it finds there is filed as a finding (§12) and recorded in a baseline file, so the clean run stays
meaningful. A rule whose findings turn out to be mostly false positives is narrowed rather than baselined. The report
lists the wallet-backend functions each rule matched, so a clean run can't come from matching nothing.

## 9. Indexer-hardening guide

The guide is written for developers.stellar.org. It follows the RFP's fixed outline:
1. which transaction fields stellar-core validates (signatures, sequence numbers, fees, time bounds) and which it
   passes through (memos, Soroban auth trees, muxed IDs). The memo and a muxed source are passed through except on a
   single-operation `InvokeHostFunction` from protocol 25, where core rejects them; the table records that exception.
   This is a field-by-field table over the fields an indexer reads: transaction and operation sources (including muxed
   IDs), sequence numbers, fees, time bounds, signatures, memos, the account, asset and amount fields of operation
   bodies, and Soroban auth entries and footprints. Each row gives the stage (validation, apply or Soroban host) and
   its evidence, and is checked against the manifest;
2. recommended depth and size caps, each derived from the limit it protects against. For example, the nesting depth
   for `ScVal` follows the XDR depth limit that rs-stellar-xdr and the Soroban host enforce at the pinned version;
3. deriving participants from the meta: ledger-entry changes and fee processing, with worked examples from the
   corpus;
4. muxed and signed-payload handling, including SEP-23 strkey forms and column sizes (`M…` 69 chars, `B…` 58, `P…`
   up to 165);
5. a self-audit checklist mirroring the three linter rules, for indexers in other languages.

Publication requires review by a stellar-core or platform engineer. We request that review as soon as the draft,
with the field table, exists, and address every comment. If no reviewer is assigned within two weeks of the request,
we ask SCF to name one. The guide is delivered ready to publish, as a pull request to the Stellar developer docs;
merging it is the docs maintainers' call.

## 10. CI, release and adoption

- Every tool (generator, harness, conformance runner, linter) has its own test suite.
- **On every pull request** in the tools' repos, offline:
  - round-trip, manifest freshness, schema and the second-decoder cross-check, over the whole corpus;
  - regeneration of entries whose generator changed;
  - the harness against wallet-backend and the conformance runner against all three SDKs, on the changed entries
    plus a fixed smoke set (the five sample entries).
- **Nightly:** the harness and the conformance runner over the whole corpus.
- **At each release:** regeneration of every generated entry under both passphrases.
- A **GitHub Action** lets any indexer or SDK run the corpus in its own CI. It is the cheapest way for a third-party
  indexer to adopt the kit. It ships with 1.0 but is not an acceptance item.
- **Adoption starts with SDF's own pipeline:** we offer wallet-backend's maintainers the corpus check for their CI,
  as a pull request if they want one.
- Releases are tagged; corpus releases are versioned by the newest protocol covered.

## 12. Findings and disclosure

**Findings report.** One row per finding:
- the issue link, or a private-advisory reference;
- the corpus entry or input vector;
- the verdict and its supporting evidence (logs, exit codes);
- severity:
  - **critical:** halts ingestion (`halted`);
  - **high:** data loss or corruption;
  - **medium:** a decoding divergence;
  - **low:** anything else;
- the affected CAP and component.

Every failure maps to a row, with a minimal reproducing entry or input vector. A private advisory counts as filed;
the reviewer can verify it with SDF.

**Audit history.** None of our SDF-funded projects has had a third-party security audit. This kit runs offline, holds
no keys or funds and has no hosted service, so we budget no audit; its security work is the disclosure process
below.

**Disclosure.** Ingestion-halting inputs are denial-of-service vectors against production indexers. Critical and
high findings are reported privately first, through SDF's security reporting process, and to the affected
maintainers. The exact channel is confirmed with SDF at kickoff. The corpus entry that triggers such a finding is the
one exception to building in public: it is withheld until a fix is released. Publication is tracked under
maintenance if it falls after delivery. Medium and low findings are filed publicly right away.

## 13. Maintenance and protocol upgrades

Our team maintains the kit through the first protocol upgrade after the production release, as the RFP asks:
- **New CAPs:** corpus entries for the CAPs that upgrade ships.
- **Protocol bump:** every tool is bumped to the new protocol's XDR, with CI passing.
- **On testnet, best effort:** the harness and conformance runner run over the new protocol's ledgers before the
  mainnet vote.
- **Withheld entries:** published once their fix is released.
- **Issues:** triaged as they come in.

After that upgrade we continue on a best-effort basis. The corpus, manifest tool and generator are documented, so
anyone can add entries for later CAPs.
